# size-baseline.txt — the ratchet behind `checkFileSizeCaps`.
#
# A listed count is a ceiling that only shrinks. A cap that is not re-checked is not a cap.
#
# The caps (docs/contributors/code-as-art.md, "House rules -> Size") are per language:
#
#     Java / Kotlin   soft   400   hard   800   exception 1,200, with the invariant comment
#     JavaScript      soft   600   hard 1,200   exception 1,600, with the invariant comment
#     CSS             exempt. Splitting a cascade on line count is a regression risk with no
#                     readability win, so clients/web/.../style.css is deliberately absent from
#                     this file and from the guard.
#
# The three rules `checkFileSizeCaps` enforces against this list:
#
#   1. A listed file may only shrink. Its code-line count must stay <= the number below. Growing it
#      fails the build — that is the whole point of the file.
#   2. A file that is NOT listed must be <= the hard cap for its language. A new 900-line Java
#      file fails. Adding it here instead is the escape hatch, and it is a reviewable diff.
#   3. Every entry carries a comment. Every file here is at or above its hard cap, so every file
#      here is claiming the exception band, and the exception band costs a stated invariant.
#      An entry with no comment above it fails the build. Re-baselining a number upward means
#      deleting the invariant that justified the old one and writing one that justifies the new
#      one — in the same diff, right here.
#
# The band is not a second ceiling. A listed file above the exception band is named debt, not a
# moved band. The ratchet is what holds it — each listed file can only shrink from here.
#
# The count is code lines, not `wc -l`. Comments (including Javadoc), blank lines, and `package` /
# `import` lines do not count. A statement with a trailing comment still counts. String and
# text-block contents count — a fixture is data. That is the point: the cap is on behaviour in
# one file, not on the envelope `jk format` writes or the comments a type needs. Recount by
# running `./gradlew checkFileSizeCaps`; a listed file that shrank prints the tightened line.
# Imports and Javadoc cannot grow a file past the cap.
#
# This file currently has no entries — no file claims the exception band.
#
# UPDATING AFTER A SHRINK. Shrinking a listed file passes — the ratchet never blocks progress. The
# guard then prints the tightened line, e.g.
#
#     size-baseline.txt is loose (these files shrank — tighten it in this commit):
#        810  shared/wire/src/main/java/cc/jumpkick/wire/protocol/ProtoEvents.java   (was 884)
#
# Paste that number over the old one, keep or rewrite the comment, and it lands in the same commit
# as the shrink. A listed file that falls under the hard cap leaves this file entirely.

# FORMAT. One entry per line: `<code-lines>  <path from the repo root>`. The comment lines
# immediately above an entry, with no blank line between, are that entry's invariant. A blank line
# separates entries. Sorted by path.

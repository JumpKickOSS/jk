# size-baseline.txt — the ratchet behind `checkFileSizeCaps` (JK-2411).
#
# A shipped number is a floor, not a fact. `EngineServer` hit 1,064 lines at the end of its peel and
# was back to 1,240 eleven days later; the `JkManager` triad went 2,467 -> 3,414 in ten days, past
# the 2,204-line god class it replaced, before JK-2434 took it back to 2,380. A cap that is not
# re-checked is not a cap.
#
# The caps (docs/contributors/code-as-art.md, "House rules -> Size") are per language:
#
#     Java / Kotlin   soft   400   hard   800   exception 1,200, with the invariant comment
#     JavaScript      soft   600   hard 1,200   exception 1,600, with the invariant comment
#     CSS             exempt. Splitting a cascade on line count is a regression risk with no
#                     readability win, so clients/web/.../style.css (2,401 lines) is deliberately
#                     absent from this file and from the guard.
#
# The three rules `checkFileSizeCaps` enforces against this list:
#
#   1. A listed file may only shrink. Its line count must stay <= the number below. Growing it
#      fails the build — that is the whole point of the file.
#   2. A file that is NOT listed must be <= the hard cap for its language. A new 900-line Java
#      file fails. Adding it here instead is the escape hatch, and it is a reviewable diff.
#   3. Every entry carries a comment. Every file here is at or above its hard cap, so every file
#      here is claiming the exception band, and the exception band costs a stated invariant.
#      An entry with no comment above it fails the build. Re-baselining a number upward means
#      deleting the invariant that justified the old one and writing one that justifies the new
#      one — in the same diff, right here.
#
# The band is not a second ceiling, and this file does not pretend otherwise: a handful of entries
# below sit ABOVE the 1,200 exception band. They are named debt with peel tickets (JK-2433..2439),
# not a band that moved. The ratchet is what holds them — each can only shrink from here.
#
# The count is `wc -l`: newline characters, the same number the scoreboard and commit messages
# cite. Recount one file with `wc -l <path>`.
#
# UPDATING AFTER A SHRINK. Shrinking a listed file passes — the ratchet never blocks progress. The
# guard then prints the tightened line, e.g.
#
#     size-baseline.txt is loose (these files shrank — tighten it in this commit):
#        958  server/engine/src/main/java/cc/jumpkick/engine/EngineServer.java   (was 1223)
#
# Paste that number over the old one, keep or rewrite the comment, and it lands in the same commit
# as the shrink. Deleting a listed file works the same way: drop its entry.
#
# JK-2412 moved 17 of the numbers below UPWARD, by 2 to 16 lines, and 7 downward. Nothing was
# added to any of them: the tree-wide FQCN sweep replaced an inline `cc.jumpkick.foo.Bar` with an
# `import` line, so a file that named a package-qualified type in ten places gained one line and
# lost ten qualifiers. Characters fell everywhere; lines moved either way depending on how much
# re-wrapping the shorter names bought back. The invariants below are unchanged.
#
# JK-2414 moved four of them upward, by 1 to 7 lines, for the same kind of reason: the TaskNames
# sweep replaced `"compile-java"` with `TaskNames.COMPILE_JAVA`, which is eight characters longer,
# so a `case` arm or a constructor call that used to fit on one line now wraps. Two of the four are
# the added `import` line alone. The invariants below are unchanged.
#
# JK-2413 moved eleven of them upward. Ten gained exactly one line and nothing else — the `import`
# for `cc.jumpkick.lock.ManifestPaths`. `ManifestPaths.MANIFEST` is fourteen characters longer than
# `"jk.toml"`, which re-wrapped eight call sites tree-wide but none inside those ten. The eleventh,
# `BuildJournal`, moved by two: deleting its redundant `LOCKFILE` re-declaration took two lines off,
# and the one `Files.move` that named the lock twice on a single line stopped fitting, which put
# three back. The invariants below are unchanged.
#
# JK-2437 (T57) DELETED two entries rather than re-baselining them. `BuildCommand` 1,206 -> 676 and
# `NewCommand` 1,121 -> 742 are both under the 800 hard cap, so neither is claiming the exception
# band any more and neither belongs in this file. Both of the invariants they used to carry were
# false when checked: BuildCommand's claimed the lock/sync/compile/test/package order lived in the
# file (the engine owns that order — `BuildService.buildWorkspace`; the file was a renderer plus a
# process-wide ProjectInfo memo), and NewCommand's claimed a template rollback lived there (there
# is no rollback in the client at all). An invariant nobody re-derives is how a file stays big.
#
# JK-2418 moved four of them upward by exactly one line each — the `import` for
# `cc.jumpkick.host.CacheTree`. `CacheTree.ACTIONS.under(cache)` is two characters shorter than
# `cache.resolve("actions")`, so three of the four re-wrapped nothing; in `TaskForecaster` the two
# Zinc state-dir chains got a local for the tier, which cost one line and saved one. `BuildPlanner`
# is unchanged: its import cost a line and the shorter call let a wrapped constructor fit on one.
# The invariants below are unchanged.
#
# JK-2440 DELETED three entries rather than re-baselining them. app.js (2,786), code.js (1,966) and
# fold.js (1,734) are now 601, 775 and 971, under the 1,200 hard cap and off this list entirely. The
# invariants that justified them cited a cost that does not exist: `clients/web` has no bundler, but
# it has had a module system since before this file did. index.html loads exactly one script,
# `<script src="/app.js" type="module">`, and every other file is reached through a static `import`,
# so the browser orders the graph and a bad specifier is a link error. A JS split there costs an
# import line, the same as Java. What it does cost is checked by clients/web/src/test/js/
# shell.test.mjs: one entry point, no orphan module, and no name the in-DOM template calls that the
# root component has stopped providing.
#
# JK-2438 DELETED three engine entries rather than re-baselining them. BuildPlanner (1,251 -> 777),
# BuildJournal (837 -> 776) and ImagePlans (809 -> 797) are all under the 800 hard cap and off this
# list. None of the three shrank by splitting: BuildPlanner lost a 425-line facade — 83 members under
# 74 names, every one of them a single statement forwarding its own parameters, in their own order, to
# PlannerTails / PlannerKsp / PlannerNative / PlannerPlugin / PlannerCompile / PlannerPackage /
# PlannerLang / PlannerResources / PlannerSupport — plus the middle rung of a three-deep Inputs
# constructor chain that no caller used. Thirty-one of the 83 had no caller through the facade at all;
# the rest now name their owner in an `import static`, which is the point: a wildcard
# `import static BuildPlanner.*` in twelve collaborators let any of them reach any other's helper
# through a file that owned none of it. BuildJournal lost `appendHostSamples` (no
# caller anywhere, and the sole writer of the `host.` keys MetricsHarvest still reads) together with
# the METRICS_LOCKS map whose only reason to exist was that method racing `complete()`; ImagePlans
# stopped re-deriving `Lockfile.Artifact.checksumHex()` by hand in two places.
#
# The invariants those three used to carry did not survive checking. BuildPlanner's said "coreBuilder
# and appendDeclaredTails have to agree on DAG edge order" — appendDeclaredTails has lived in
# PlannerTails for some time and BuildPlanner only forwarded to it, so the two halves were already in
# different files and the entry was defending a pairing that no longer existed. BuildJournal's said
# "the append path and the replay path must read and write the same record shape" — true, and both
# are well under the cap now that a dead third writer is gone. ImagePlans' is unchanged in substance
# and simply no longer needs an exception band.
#
# One BuildPlanner finding is worth keeping so it is not re-filed: the 5-argument
# `PlannerSupport.testStampExtras` overload is NOT dead. Only the BuildPlanner trampoline in front of
# it was; the owner's own 4-argument overload calls the 5-argument one, which is why deleting the
# facade removed the trampoline without touching the overload.
